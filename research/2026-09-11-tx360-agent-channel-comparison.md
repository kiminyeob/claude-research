# TX360 AI 에이전트 — 채널 후보 비교

> 작성일 2026-09-11 · 목적: **최종 후보를 좁히기 위한 논의 자료**
> 이 문서는 PoC 결과 보고서가 아니다. 공개 문서를 근거로 후보를 같은 기준에 놓고 비교한 것이다.

## 0. 한 장 요약

**하려는 일** — 사내망 전용 시스템인 TX360의 정보·콘텐츠를 임직원이 AI 에이전트로 **조회**하게 한다. 이후 단계로 **등록**까지 확장한다.

**이번 조사의 결론 한 문장**

> 병목은 "어느 채널에서 쓰게 할까"가 아니라 **"사내망을 어떻게 넘을까"**다.

이유는 단순하다.

- Claude에 등록하는 **리모트 커넥터의 호출은 사용자 PC가 아니라 Anthropic 클라우드에서 나간다.** 따라서 인터넷에 노출되지 않은 TX360에는 **닿지 않는다.** 실제로 TX360 호스트는 **공개 DNS에서 조회조차 되지 않는다**(이 조사에서 NXDOMAIN 확인).
- 사내망에 바로 닿을 수 있는 Claude 채널은 **로컬 MCP를 띄울 수 있는 Claude Code와 Claude Desktop뿐**이다.
- 그런데 그 둘은 **일반 업무 사용자용 도구가 아니다.**

즉 **"일반 사용자 편의성"과 "사내망 도달"이 정면으로 충돌한다.** 이 충돌을 어떻게 푸느냐가 곧 채널 선택이다.

**푸는 방법은 세 갈래뿐이다**

| 갈래 | 해법 | 해당 후보 |
|---|---|---|
| ① 사내 플랫폼이 대신 넘는다 | 사내망 안에 있는 플랫폼이 MCP를 품고, 외부로는 모델만 호출 | FabriX 에이전트, Brity Copilot |
| ② 우리가 직접 넘는다 | 사내 서버에서 에이전트를 돌리고 화면도 우리가 만든다 | Agent SDK 사내 호스팅, TX360 내장, Knox 봇 |
| ③ 경계를 연다 | TX360 MCP를 DMZ에 노출하거나 터널을 뚫는다 | Claude 웹 챗·Cowork + 커넥터 |

**잠정 권고**

- **단기 검증용**: Claude Code. 사내 PC에서 로컬 MCP로 TX360에 바로 붙으므로, 별도 인프라 없이 "이 검색 경험이 쓸 만한가"를 가장 빨리 확인할 수 있다.
- **최종 배포 1순위 후보**: FabriX 에이전트. 사내 플랫폼이라 ①에 해당하고, 이미 기술지원 요청이 접수돼 있다.
- **조건부 최단 경로**: Brity Copilot. 이미 사내 메신저에 들어와 있다면 새로 만들 필요가 없을 수 있다.

**단, 확정 전에 반드시 확인할 세 가지**

1. 사내에 **Claude Enterprise가 이미 제공되고 있는가?** — 삼성SDS·Anthropic 파트너십으로 관계사에 제공 중이라는 보도가 있다. 사실이면 과금 전제가 통째로 바뀐다. `[미검증]`
2. **Brity Copilot이 이미 사내 메신저에 들어와 있는가?** — 있다면 "지식소스 등록"이 가장 빠른 길일 수 있다. `[미검증]`
3. **FabriX가 TX360 MCP를 실제로 물 수 있는가?** — 기술지원 회신으로 확인. 이때 **TLS 설정 문제를 반드시 함께 물어야 한다**(2절 마지막 참조).

## 1. 용어 정리

논의 전에 용어부터 맞춘다. 각 항목은 **정의 / 비유 / 이건 아님** 세 줄이다.

### 연결에 관한 용어

**MCP (Model Context Protocol)**
- **정의**: AI가 외부 시스템의 기능과 데이터를 쓸 수 있게 해 주는 표준 규약.
- **비유**: 노트북과 주변기기를 잇는 USB 규격.
- **이건 아님**: AI 모델도 아니고 제품 이름도 아니다. 규격일 뿐이다.

**MCP 서버**
- **정의**: TX360의 기능을 MCP 규격으로 내놓는 프로그램. "검색해줘", "문서 가져와줘" 같은 도구 목록을 제공한다.
- **비유**: TX360에 꽂는 USB 어댑터.
- **이건 아님**: AI가 아니다. 스스로 판단하지 않고 요청받은 기능만 수행한다.

**커넥터 (Connector)**
- **정의**: Claude 제품에 "이 MCP 서버를 쓰겠다"고 등록해 둔 것.
- **비유**: 휴대폰에 블루투스 기기를 페어링해 두는 것.
- **이건 아님**: 커넥터가 기능을 만들어 내지는 않는다. 이미 있는 MCP 서버를 가리킬 뿐이다.

**로컬(stdio) MCP vs 리모트 MCP** ← 이 문서에서 가장 중요한 구분
- **로컬**: 사용자 PC 안에서 프로그램으로 실행된다. Claude가 그 PC에서 직접 띄운다. → **사내망 접근 가능**
- **리모트**: 인터넷 주소(`https://...`)로 접속한다. **Anthropic 클라우드가 접속한다.** → **사내망 접근 불가**
- **비유**: 로컬은 내 책상 위 프린터, 리모트는 인터넷 인쇄소에 맡기는 것.
- **이건 아님**: "내 노트북에서 Claude 앱을 쓰니까 내 회사 네트워크로 나가겠지" — **리모트 커넥터에는 틀린 생각이다.**

### 확장·배포에 관한 용어

**스킬 (Skill)**
- **정의**: "이럴 땐 이렇게 해라"를 적어 둔 설명서 묶음. Claude가 필요할 때 읽는다.
- **비유**: 신입에게 주는 업무 매뉴얼.
- **이건 아님**: **네트워크 권한을 주지 않는다.** 매뉴얼이 잠긴 문을 열어 주지는 않는다. `[검증됨]`

**플러그인 (Plugin)**
- **정의**: 스킬·커넥터·명령어 등을 한 묶음으로 포장한 배포 단위.
- **비유**: 앱스토어에서 받는 앱 하나.
- **이건 아님**: 새 능력을 만드는 게 아니라 있는 것들을 묶어 배포하기 쉽게 한 것이다.

**마켓플레이스 (Marketplace)**
- **정의**: 플러그인을 모아 두고 조직 구성원이 설치하게 하는 배포처.
- **비유**: 사내 앱스토어.
- **이건 아님**: 결제나 거래 기능이 아니다. 목록과 설치 경로일 뿐이다.

**서브에이전트 (Subagent)**
- **정의**: 큰 일을 나눠 맡기는 보조 AI. 본체가 지시하고 결과만 받는다.
- **비유**: 팀장이 팀원에게 조사 업무를 떼어 주는 것.
- **이건 아님**: 별도 계정이나 별도 라이선스가 아니다.

**훅 (Hook)**
- **정의**: "이 시점에 이 명령을 자동 실행"하는 자동화 규칙.
- **비유**: 정해진 시각에 자동으로 켜지는 조명 타이머.
- **이건 아님**: AI가 판단해서 하는 게 아니라, 조건이 맞으면 기계적으로 실행된다.

### 화면에 관한 용어

**MCP Apps (인터랙티브 커넥터)**
- **정의**: 대화창 안에 카드·표·버튼 같은 화면을 띄우는 확장 규격.
- **비유**: 채팅방 안에서 열리는 미니 웹페이지.
- **이건 아님**: 모든 Claude 제품이 지원하지는 않는다. 3절 표 참조.

**Artifact**
- **정의**: Claude가 만든 문서·표·웹페이지를 대화 옆 패널에 펼쳐 보여 주는 기능.
- **비유**: 회의 중 옆에 띄우는 화이트보드.
- **이건 아님**: 우리 시스템에 연결하는 수단이 아니다. 결과를 보여 주는 방식일 뿐이다.

**프로젝트 (Project)**
- **정의**: 관련 대화와 자료를 묶어 두는 claude.ai의 작업 공간.
- **비유**: 업무별 폴더.
- **이건 아님**: 에이전트를 조직에 배포하는 수단이 아니다.

### 제품·서비스에 관한 용어

**Claude Code**
- **정의**: 터미널·IDE에서 쓰는 에이전트형 Claude. 파일을 읽고 명령을 실행한다.
- **비유**: 옆자리에 앉아 직접 키보드를 잡는 개발자.
- **이건 아님**: 코딩 전용 도구이긴 하나, 이 논의에서는 **사내망 MCP를 바로 붙일 수 있는 검증 도구**로서 의미가 있다.

**Cowork**
- **정의**: Claude Code의 엔진을 비개발자 업무(조사·문서 작성·자료 정리)에 맞춰 내놓은 별도 서피스.
- **비유**: 같은 엔진에 세단 차체를 씌운 차.
- **이건 아님**: 채팅의 한 모드가 아니다. **별도 서피스**다. `[미검증]`

**Agent SDK**
- **정의**: Claude Code의 알맹이(질문 → 도구 호출 → 결과 해석 → 답변 반복 루프)를 Python·TypeScript 라이브러리로 떼어낸 것.
- **비유**: 완제품 자동차에서 **엔진만** 사 오는 것. 차체·핸들·좌석(= 화면·로그인·운영)은 우리가 만든다.
- **이건 아님**: 화면도 로그인도 들어 있지 않다. "SDK를 쓰면 앱이 생긴다"가 아니다. `[검증됨]`

**Managed Agents**
- **정의**: 에이전트 루프와 실행 환경까지 Anthropic이 대신 돌려 주는 서버측 에이전트 서비스.
- **비유**: 엔진도 차체도 빌리고, 어디로 갈지만 우리가 지시하는 렌터카.
- **이건 아님**: Agent SDK와 다르다. 이쪽은 **호스팅까지 남이 한다.** `[검증됨]`

**시트 (Seat)**
- **정의**: 임직원 1인에게 배정되는 Claude 이용 권한. 사용량 한도가 딸려 있다.
- **비유**: 1인 1좌석 정기권.
- **이건 아님**: 우리가 만든 앱의 사용자에게 이 좌석을 쓰게 할 수 **없다.** 약관상 금지돼 있다. `[검증됨]`

### 세 줄로 압축하면

1. **커넥터는 연결**, **스킬은 사용법**, **플러그인은 포장**, **마켓플레이스는 배포처**다. 네 개는 층이 다르다.
2. **Cowork는 채팅의 모드가 아니라 별도 서피스**다.
3. **Agent SDK는 우리가 호스팅, Managed Agents는 Anthropic이 호스팅**한다.

## 2. 결정은 3층으로 나눠서 한다

후보를 뒤섞어 놓고 비교하면 결론이 안 난다. 세 축은 **서로 독립**이므로 따로 정해야 한다.

| 층 | 질문 | 선택지 |
|---|---|---|
| **A. 사용자 채널** | 임직원이 어디서 쓰는가 | Claude 웹 챗 · Desktop · Cowork · Claude Code · FabriX · 자체 웹앱 · TX360 내장 · Knox 메신저 |
| **B. TX360 연결 경로** | 사내망을 어떻게 넘는가 ← **병목** | 로컬 MCP · DMZ 노출 · MCP Tunnel · self-hosted sandbox · 플랫폼 내부 호스팅 · 자체 백엔드 |
| **C. 모델 호출·과금** | 누가 모델 값을 내는가 | 임직원 시트 · API 종량제 · Bedrock/Vertex 경유 |

같은 채널이라도 B와 C를 뭘로 고르냐에 따라 난이도와 비용이 완전히 달라진다. 그래서 표를 한 장으로 합치지 않고 나눠 본다.

### B층 — 사내망을 넘는 여섯 가지 방법

| 방법 | 사내망 도달 | 대가 | 성숙도 |
|---|---|---|---|
| **로컬(stdio) MCP 직결** | ✅ 사용자 PC가 사내망 안에 있으므로 방화벽 구멍 불필요 | 사용자마다 설치·설정 필요. 일반 사용자에게 부담 | 정식 기능 `[검증됨]` |
| **DMZ 공개 + IP 허용** | ✅ | TX360 MCP를 인터넷에 노출. `160.79.104.0/21` 허용 필요. 보안 심의 부담 최대 | 정식 기능 `[검증됨]` |
| **MCP Tunnel** | ✅ 아웃바운드 전용이라 인바운드 개방 불필요 | **claude.ai에서는 못 쓴다.** Console Managed Agents·Messages API 전용 | **research preview** — 가용성·지속성 보장 없음 `[검증됨]` |
| **Managed Agents self-hosted sandbox** | ✅ 도구 실행이 사내 인프라에서 일어남 | 모델 추론은 여전히 Anthropic. 도구 입출력은 Anthropic 컨트롤 플레인으로 흐름 | 베타 `[검증됨]` |
| **사내 플랫폼 내부 호스팅 (FabriX)** | ✅ 플랫폼이 사내망 안에 있음 | 플랫폼이 제공하는 기능 범위에 종속 | 회신 대기 `[미검증]` |
| **자체 백엔드** | ✅ | 화면·인증·운영·로그를 전부 우리가 만듦 | 정식 `[검증됨]` |

> **꼭 기억할 것**: 어떤 방법을 쓰든 **검색 결과 본문은 모델이 있는 클라우드로 전송된다.** 로컬 MCP를 써도 마찬가지다. 네트워크 경계는 옮겨지지만 **데이터 경계는 그대로**다. 보안 심의에서 가장 많이 오해되는 지점이다.

### 현재 연결 설정이 말해 주는 것

지금 쓰고 있는 TX360 MCP 설정을 뜯어보면 위의 논의가 훨씬 구체적으로 좁혀진다. 구성을 요약하면 (내부 주소·키는 생략):

- 사용자 PC에서 `npx`로 **`mcp-remote`** 라는 외부 브리지 패키지를 실행한다
- 그 브리지가 TX360의 **`/sse` 엔드포인트**에 HTTPS로 접속한다
- 인증은 **개인 API 키를 `Authorization: Bearer` 헤더**로 전달한다
- 환경변수로 **사내 프록시를 지정하고, TX360 도메인만 프록시를 우회**해 직접 연결한다
- `NODE_OPTIONS`로 **TLS 보안수준을 낮추고(`SECLEVEL=0`) 시스템 인증서 저장소를 쓰도록** 한다

여기서 여섯 가지 사실이 나온다.

**1. TX360은 정말로 사내망 전용이다 — 공개 DNS에도 없다** `[검증됨]`

이 세션에서 조회해 본 결과 TX360 호스트와 그 상위 도메인 모두 **공개 DNS에서 응답이 없다(NXDOMAIN).** 방화벽에 막히는 수준이 아니라 **Anthropic 클라우드는 이 호스트의 이름조차 찾을 수 없다.** 리모트 커넥터가 불가능한 이유가 이것으로 확정됐다.

**2. TX360 MCP는 원래 "리모트 MCP 서버"다. 로컬 MCP가 아니다** `[검증됨]`

`mcp-remote`는 "로컬 전용 클라이언트가 리모트 서버에 접속할 수 있게 해 주는 프록시"로 소개된 패키지다. 즉 TX360은 **HTTP 엔드포인트를 가진 리모트 서버**이고, 사용자 PC에서 도는 것은 **중계기**다.

- **좋은 소식**: 네트워크 도달 문제만 풀리면 구조적으로는 어느 채널에든 붙일 수 있다. MCP 서버를 새로 만들 필요가 없다.
- **나쁜 소식**: 지금 동작하는 이유가 **"사내 관리 PC에서 도는 Node 프로세스라서"**다. 그 전제가 깨지는 채널에서는 현재 설정을 그대로 쓸 수 없다.

**3. 현재 설정의 대부분이 PC 환경에 의존한다** ← 이 절에서 가장 중요한 발견

프록시 지정, 프록시 우회 목록, TLS 완화, 시스템 인증서 사용 — 네 가지 모두 **사내 관리 PC이기 때문에 가능한 설정**이다. 그런데 **Anthropic 클라우드 커넥터에도, FabriX에도, Managed Agents에도 `NODE_OPTIONS`를 넣을 자리가 없다.**

→ 만약 TX360의 TLS 구성이 표준 클라이언트가 거부하는 형태라면, **인증이나 네트워크를 따지기 전에 TLS 핸드셰이크 단계에서 먼저 실패한다.**

→ **확인 필요 (기술지원 질의 1순위)**: `SECLEVEL=0`이 필요한 이유가 무엇인가? 구형 암호화 스위트인가, SHA-1 서명인가, 짧은 키인가, 구버전 TLS인가? 이걸 모르면 **FabriX 연계도 같은 지점에서 막힐 수 있다.**

**4. 인증이 이미 "개인 키"다 — 권한 모델 논의의 출발점이 바뀐다**

공통 서비스 계정이 아니라 **임직원 개인 API 키**를 쓰고 있다. 즉 **사용자별 권한 분리가 이미 부분적으로 구현돼 있다.** 이건 좋은 출발점이다. 다만 형태가 **정적 Bearer 토큰**이라 다음 문제가 따라온다:

- 키가 **명령줄 인자**로 넘어간다 → 그 PC의 프로세스 목록에서 보인다
- 설정 파일에 평문으로 들어간다 → 배포·회수·교체 절차가 필요하다
- OAuth가 아니므로 **Claude의 조직 단위 IdP 인증(enterprise-managed auth)을 쓸 수 없다** `[미검증]`
- claude.ai 커넥터로 옮기면 정적 헤더는 **조직 공용 자격증명**이 되어 **개인별 구분이 사라질 가능성이 있다** `[미검증]`

**5. `/sse`는 사용 중단 예정인 전송 방식이다** `[검증됨]`

MCP 스펙은 HTTP+SSE를 `2025-03-26` 리비전부터 deprecated로 두었고, 현행 리비전에서 제거 대상으로 분류했다. Claude Code 문서도 "SSE는 deprecated이므로 HTTP 서버를 쓰라"고 안내한다.

→ 지금 잘 동작하는 것과 별개로 **Streamable HTTP 전환은 예정된 과제**다. 채널을 바꾸는 시점에 함께 처리하는 것이 효율적이다.

**6. 공급망 관점 — 브리지 버전이 고정돼 있지 않다**

`npx -y mcp-remote`는 버전을 지정하지 않아 **실행 시점의 최신 버전을 내려받는다.** 그리고 `mcp-remote`는 Anthropic이나 삼성SDS가 아닌 **외부 MIT 라이선스 패키지**다. `[검증됨]`

→ 특정 릴리스가 오염되면 **임직원 PC에서 개인 API 키를 손에 쥔 채 실행**된다. 최소한 **버전 고정**과 **사내 레지스트리 미러링**을 검토해야 한다.

### 이 분석이 후보 비교에 주는 영향

| 후보 | 새로 드러난 쟁점 |
|---|---|
| ① 웹 챗 | 공개 DNS에도 없으므로 **DMZ 노출이 사실상 유일한 길**. 노출한다면 TLS 정상화도 함께 필요 |
| ② Desktop · ④ Claude Code | **현행 설정이 이미 이 방식**이다. 추가 작업 없이 지금 동작한다 |
| ③ Cowork | 리모트 커넥터만 가능하다면 ①과 같은 제약을 받는다 |
| ⑤ FabriX | **TLS 완화 없이 접속되는지가 관문.** 기술지원 질의에 반드시 포함해야 한다 |
| ⑥⑦⑧⑨ 자체 구축 | 우리 서버이므로 프록시·TLS·인증서를 직접 통제할 수 있다 → **이 제약에서는 자유롭다** |

> 2번이 없으면 **양방향 에이전트는 불가능**하고, 3번만 있으면 **단방향 알림 봇**까지가 한계다. 이것이 비기술 팀원에게 전달할 핵심 한 문장이다.

### ⑩ Brity Copilot 지식소스 등록 — 조건부 후보

| 항목 | 내용 |
|---|---|
| **한 줄 정의** | 이미 사내에 도입된(또는 도입 예정인) Brity Copilot에 TX360을 지식소스로 붙이는 방식 |
| **사용자 동선** | 이미 쓰고 있는 메신저·메일 안의 검색 기능 그대로. **새로 배울 것이 없음** |
| **기술 제약** | **도입 여부 자체가 확인되지 않음.** Brity Copilot이 메신저에서 "지식 검색"을 제공한다는 보도는 있으나 사내 도입 현황은 확인 필요 `[미검증]` |
| **확장 수단** | 플랫폼이 허용하는 지식소스 등록 범위에 종속 |
| **구현 복잡도** | **가장 낮을 가능성** — 이미 있다면 등록만 하면 됨. 없다면 후보에서 탈락 |
| **모델 호출·과금** | 플랫폼 계약에 포함 |

> 이 후보는 **확인 결과에 따라 최단 경로이거나 아예 없는 선택지**다. 그래서 조건부로 둔다. 확인 비용이 거의 들지 않으므로 가장 먼저 물어볼 가치가 있다.

### 세 가지 과금 경로

> **중요**: **자체 구축 계열(⑥⑦⑧⑨)은 시트를 쓸 수 없다.** Anthropic이 자사 제품에 claude.ai 로그인·사용량을 쓰는 것을 약관으로 금지하고 있다. 선택의 여지가 없는 제약이다. `[검증됨]`

### 시트 방식의 숨은 리스크

- **채팅·Claude Code·Cowork가 좌석 한도 한 풀을 공유한다.** TX360 검색만 쓰는 게 아니라 다른 용도와 경쟁한다. `[검증됨]`
- **Claude Code와 Cowork는 일반 채팅보다 토큰을 훨씬 빨리 소모한다.** 문서 표현으로 "디버깅 한 세션이 채팅 하루치보다 많이 쓸 수 있다". `[검증됨]`
- 한도 초과분은 **API 요율로 별도 청구**된다. 즉 시트 방식이라고 비용이 고정되는 게 아니다. `[미검증]`

### API 종량제 — 개략 비용 예시

아래는 **가정에 기반한 계산 예시**다. 실제 값은 사용 패턴 측정 후 다시 잡아야 한다.

**가정**: 사용자 200명 · 1인당 하루 5회 검색 · 월 20 영업일 → **월 20,000회**
**1회당**: 입력 8,000 토큰(시스템 프롬프트 + 도구 정의 + 검색 결과 본문) · 출력 700 토큰
→ 월 입력 160M 토큰 · 월 출력 14M 토큰

| 모델 | 입력 비용 | 출력 비용 | **월 합계** |
|---|---|---|---|
| Opus 5 ($5 / $25) | $800 | $350 | **약 $1,150** |
| Sonnet 5 ($2 / $10) | $320 | $140 | **약 $460** |
| Haiku 4.5 ($1 / $5) | $160 | $70 | **약 $230** |

**최적화를 적용하면** — 시스템 프롬프트와 도구 정의는 매번 같으므로 프롬프트 캐시가 잘 듣는다. 입력의 70%가 캐시 적중(단가 0.1배)한다고 보면:

| 모델 | 캐시 적용 후 월 합계 |
|---|---|
| Sonnet 5 | 약 **$258** (캐시 미적용 대비 **44% 절감**) |

추가 수단: 검색 요약처럼 단순한 작업은 **Haiku 4.5**로 내리고, 실시간성이 필요 없는 대량 처리는 **Batch(50% 할인)**를 쓴다. 두 할인은 중첩 적용된다. `[검증됨]`

> **판단**: 200명 규모에서 API 종량제는 **월 수백 달러 수준**이다. 비용이 채널 선택의 결정 요인이 되기는 어렵다. **편의성·보안·구현 복잡도가 훨씬 큰 변수다.**

### ⚠️ 선결 확인 — 사내 Claude 계약 상태

2026년 7월 **삼성SDS와 Anthropic이 전략적 파트너십을 체결**했고, **삼성 관계사 20곳 약 7만 명에게 Claude Enterprise를 제공 중**이라는 보도가 있다. `[미검증 — 언론 보도 기준]`

사실이라면:
- 임직원 시트가 **이미 확보돼 있을 수 있다** → ①②③④의 과금 전제가 바뀐다
- 다만 **FabriX 경유와 Claude Enterprise 직접 제공은 별개 라인**이다. Claude가 FabriX의 선택 가능 모델에 포함되는지는 **공개 근거가 없다.** `[미검증]`

**이 축의 논의는 사내 Claude 계약 담당 확인 전까지 확정할 수 없다.**

## 7. 확인 요청 목록

이 문서로 닫히지 않는 것들이다. **사람이 물어봐야 답이 나온다.**

### 7-1. FabriX 기술지원 회신으로 받을 항목 (접수 완료 상태)

1. FabriX 안에서 **외부 시스템 연계 MCP 서버를 호스팅**할 수 있는가? 아니면 이미 있는 MCP 서버를 **등록·연결**만 하는 방식인가?
2. **⚠️ TLS 관문** — TX360은 현재 클라이언트 쪽에서 TLS 보안수준을 낮춰야 접속된다. FabriX에서 이런 서버에 접속할 수 있는가? 사용자 지정 CA·암호화 스위트 설정이 가능한가? **불가능하다면 TX360 서버 쪽 TLS를 먼저 정상화해야 한다.**
3. **인증 전달** — 임직원 **개인 API 키**를 사용자별로 전달할 수 있는가, 아니면 에이전트 단위 공용 자격증명만 되는가? 후자라면 사용자별 권한 분리가 불가능해진다.
4. **사용자 신원** — 에이전트가 MCP 서버를 호출할 때 **호출한 임직원이 누구인지** 백엔드로 전달되는가?
5. **전송 방식** — `/sse`(HTTP+SSE)를 지원하는가? Streamable HTTP도 지원하는가?
6. **결과 표현** — 제목·요약·원문 링크 목록을 어떻게 렌더링하는가? 페이지 이동·정렬 같은 상호작용이 가능한가?
7. **모델** — 에이전트가 호출할 수 있는 LLM 목록은? **Claude가 포함되는가?**
8. **과금 주체** — 모델 호출 비용은 플랫폼 계약에 포함되는가, 부서 부과인가?
9. **감사·운영** — 누가 무엇을 질의했는지 로그가 남는가? 보관 기간은? 에이전트 버전 관리·롤백은?
10. **응답 크기 제한** — 도구 응답 본문 크기 상한이 있는가?

### 7-2. Knox 협업솔루션 담당자 질의

1. Knox Teams / Knox Messenger에 **봇 계정 또는 서비스 계정**을 발급받을 수 있는가? 신청 창구는 어디인가?

## 8. 권고와 다음 결정

### 8-1. 지금 말할 수 있는 것

**구조적으로 탈락에 가까운 후보**

- **① Claude 웹 챗** — TX360이 공개 DNS에도 없으므로 DMZ 노출이 유일한 길이다. 노출이 심의를 통과하지 못하면 **후보가 아니다.**
- **③ Cowork** — ①과 같은 제약을 받을 가능성이 높고, 그마저도 근거가 확인되지 않았다.

**검증 도구로 쓸 후보**

- **④ Claude Code** — 이미 동작하고 있다. 추가 인프라 없이 **"이 검색 경험이 실제 업무에 쓸 만한가"**를 가장 싸게 확인할 수 있다. 다만 **일반 사용자용 최종 채널은 아니다.**

**최종 배포 후보 (확인 결과에 따라 순위 변동)**

1. **⑩ Brity Copilot 지식소스 등록** — 이미 도입돼 있다면 압도적으로 빠르다. **확인 비용이 거의 0이므로 가장 먼저 물어볼 것.**
2. **⑤ FabriX 에이전트** — 사내 플랫폼이라 사내망 문제가 구조적으로 해소되고, 노코드로 만들 수 있으며, 이미 기술지원이 접수돼 있다. **TLS 관문만 통과하면 1순위.**
3. **⑥ Agent SDK 사내 호스팅 / ⑧ TX360 내장** — 위 둘로 요구사항이 충족되지 않을 때의 카드. 통제력은 최고지만 만들 것이 가장 많다.

**보류**

- **⑦ Managed Agents** — 베타이고 ZDR 대상이 아니다. ⑥ 대비 이점이 사내망 상황에서 크지 않다.
- **⑨ Knox 봇** — 공개 근거가 전혀 없다. Knox 쪽 전제조건 확인 전까지는 평가 자체가 불가능하다.

### 8-2. 단기와 최종을 분리한 제안

| 구분 | 채널 | 목적 |
|---|---|---|
| **단기 (지금~회신 전)** | ④ Claude Code | 검색 품질·프롬프트·결과 형식을 확정한다. 여기서 만든 지시문이 어느 채널로 가든 재사용된다 |
| **중기 (회신 후)** | ⑤ FabriX (또는 ⑩) | 같은 시나리오를 같은 기준으로 재현해 비교한다 |
| **최종** | 확인 결과에 따라 결정 | 앞의 둘로 안 되는 요구사항이 확인됐을 때만 ⑥·⑧을 검토한다 |

> **중요**: 단기 검증에서 만드는 산출물(검색 지시문, 결과 형식, 잘 되는 질문·안 되는 질문 목록)은 **채널과 무관한 자산**이다. 채널이 바뀌어도 버려지지 않는다. 그래서 회신을 기다리는 동안 놀 필요가 없다.

### 8-3. 다음 회의에서 결정할 것

1. **DMZ 노출을 검토 대상에 둘 것인가, 아예 배제할 것인가** — 배제하면 후보가 절반으로 준다. 가장 먼저 정해야 할 갈림길이다.
2. **권한 모델** — 현재 개인 API 키 방식을 유지·확장할 것인가, PoC는 공통 범위로 단순화할 것인가
3. **TX360 서버 TLS 정상화 작업을 착수할 것인가** — 여러 후보의 공통 전제조건이다
4. **1차 성공 기준** — 무엇이 되면 "쓸 만하다"고 판단할 것인가 (정확도? 단계 수? 응답 시간?)
